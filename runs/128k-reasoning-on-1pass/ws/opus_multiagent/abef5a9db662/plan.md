Key insight: the map `x → f(x)` (rating after all contests) is non‑decreasing at every stage, so if we keep the current ratings of all (distinct) query start values in sorted order, the set of ratings lying in `[L_i, R_i]` is always a **contiguous index range**, and adding 1 to that range preserves sortedness (never crosses the neighbours). So compress the queries to their distinct sorted values `v_1<…<v_M` (M ≤ 3·10⁵), keep the current rating array `V[1..M]` implicitly through its difference array `D` (all `D[k] ≥ 0` always) inside a Fenwick tree, so `V[p] = prefix(p)`. For each contest `(L,R)`: find `i = first index with V ≥ L` and `j = (first index with V ≥ R+1) − 1` using Fenwick binary‑lifting search in O(log M); if `i ≤ j` do `D[i] += 1`, `D[j+1] -= 1` (two Fenwick point updates). Total O((N+Q) log M); at the end rebuild `D` from the tree in O(M), take a cumulative sum to get final ratings, and answer each query by lookup of its compressed index. Code must be tight (inlined loops, `sys.stdin.buffer.read()`, joined output) because N=2·10⁵ contests × ~4 Fenwick walks is ~1.5·10⁷ inner steps in CPython.
