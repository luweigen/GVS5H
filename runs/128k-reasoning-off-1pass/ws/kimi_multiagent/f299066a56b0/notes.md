
## ideation
Core difficulty: We need to select K disjoint pairs (top, bottom) with 2*top <= bottom, maximizing K. This is a bipartite matching on a sorted array, which admits a greedy/feasibility-check structure.

Key structural insight: In an optimal solution, we can assume the K tops are the K smallest mochi used and the K bottoms are the K largest used. Moreover, pairing the i-th smallest top with the i-th smallest bottom (among chosen ones) is optimal by an exchange argument. So a feasibility check for a given K reduces to: for all i in [0, K), 2*A[i] <= A[N-K+i]. If this holds, K pairs are achievable; if it fails for some i, then K is infeasible (because any valid matching would need the i-th smallest top matched to a bottom at least as large as the i-th smallest available large mochi).

This feasibility predicate is monotone in K (if K works, any K' < K works), so binary search over K in [0, N//2] works in O(N log N). Alternatively, a direct two-pointer greedy (top pointer from start, bottom pointer from N//2 or from start) also works in O(N): iterate bottoms from left to right, and for each bottom, match it with the smallest unmatched top if possible. Actually the cleanest O(N) greedy: t = 0 (top index), iterate b over all indices as potential bottoms; if 2*A[t] <= A[b], match and t++. But careful: tops and bottoms must be disjoint — using the same element twice. With t always < b this is fine since t only advances after matching and b moves forward; but t could catch up to b? If t == b, we'd be using A[b] as both top and bottom. Need to ensure t < b before matching. Since each match consumes one top (small index) and one bottom (current index), and t increments only on match, t <= number of matches so far <= b's iteration count... Actually t can equal b: e.g., all elements equal, t stays 0 until a match never happens — fine. But consider A = [1, 2]: t=0, b=0: 2*1 <= 1? No. b=1: 2*1 <= 2 yes, match, t=1. Answer 1. Correct. Consider A=[1,1,2]: b=0: no (2<=1 false). b=1: 2*A[0]=2<=1? no. b=2: 2<=2 yes, t=1. Answer 1. Correct — pairs (A0, A2). The danger: t index element might already be used as a bottom? t only advances past matched tops, and matched tops are indices < b at match time... when we match at bottom b, top t must satisfy t < b for disjointness. Is t < b guaranteed? t counts matches made, each match used a distinct earlier bottom, so t <= b (number of bottoms seen so far is b, matches made t <= b). If t == b, then all previous elements are matched tops... e.g., A=[1,2,100]: b=0 no; b=1: match t=0->1; b=2: t=1, check 2*A[1]=4<=100 yes, match, t=2. Answer 2? But we only have 3 elements, K max is 1! Bug: A[1] used as bottom in first pair and top in second pair. So must guard t < b. With guard: at b=2, t=1 < 2, match allowed — still wrong! Because A[1] was used as bottom at b=1. Hmm, t=1 means A[1] is the next top candidate, but A[1] was consumed as a bottom. So this naive greedy is broken. The correct approach is the split-based one: tops come from first half, bottoms from second half — i.e., two pointers i in [0, N//2), j in [N//2, N); greedily match A[i] with smallest valid A[j]. That's the standard known-correct greedy for this problem (ABC arc/typical "kagamimochi" problem). Or binary search with the check above, which is clearly correct and simple. N=5e5, O(N log N) trivially fast.

Pitfalls:
- The disjointness issue above — don't use the naive single-pass greedy without the half-split.
- Overflow not an issue in Python.
- Binary search bounds: lo=0, hi=N//2.
- Feasibility check: all(2*A[i] <= A[N-K+i] for i in range(K)) — O(K) per check, total O(N log N) fine. Could early-exit.
