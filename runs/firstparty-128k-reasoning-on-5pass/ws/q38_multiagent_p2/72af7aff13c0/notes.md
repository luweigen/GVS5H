- **Orientation choice:** Parse all queries first and count original U/D/L/R. In the original orientation, vertical moves are U/D and cost O(W0). In the transposed orientation, original L/R become vertical and cost O(H0). Choose transpose if `(L+R)*H0 < (U+D)*W0`, or on tie if the transposed width `H0` is smaller. This minimizes the dominant per-query work.
- **Transpose mapping:** If transposed, new dimensions are `H=W0, W=H0`, start becomes `(sw-1, sh-1)`, and original directions map as U->L, D->R, L->U, R->D. The path-sum problem is invariant under this transpose.
- **DP meaning:** `P[r][c]` is the sum of products over paths from `(0,0)` to `(r,c)` excluding `(r,c)`. `S[r][c]` is the sum over paths from `(r,c)` to `(H-1,W-1)` excluding `(r,c)`. The total answer is `A[end] * P[end]`. A point change by `delta` changes the answer by `delta * P[x] * S[x]`.
- **Neighbor arrays:** Maintain `AP[r][c] = A[r][c-1]` and `AS[r][c] = A[r][c+1]`. When `A[r][c]` changes, update at most two neighbor entries: `AP[r][c+1]` and `AS[r][c-1]`. This removes `c-1` and `c+1` index arithmetic from the hot row loops.
- **Frontier invariant:** After each query at current cell `(r,c)`, P rows above `r` are fully valid and P row `r` prefix `0..c` is valid; S rows below `r` are fully valid and S row `r` suffix `c..W-1` is valid. Horizontal moves only extend one cell in O(1). Vertical moves complete the old row segment and compute the new row segment, total O(W).
- **Update safety:** The updated cell is excluded from the P/S values used for its coefficient. For R, P of the new cell uses the left neighbor, not the new cell. For L, S of the new cell uses the right neighbor, not the new cell. For D/U, the recomputed segments exclude the updated cell, and the old row is completed before it becomes part of the fully valid region.
- **Implementation details:** Use row lists for `A`, `P`, `S`, `AP`, `AS`. Initial DP is inlined. Vertical segment functions bind `A`, `P`, `S`, `AP`, `AS`, `W`, `MOD`, and `range` as default locals. Horizontal updates are inlined in the query loop with local row references.
- **Complexity:** Initial O(HW). Each query costs O(1) for horizontal moves and O(W) for vertical moves in the chosen orientation. With `HW <= 200000`, the orientation choice bounds the worst-case inner-loop count by about `Q * H*W/(H+W) <= ~4.5e7`, which is the practical worst case.
- **Testing:** Sample 1 and Sample 2 match by trace. A 200k-query worst-case test is expected to run within the intended time because the dominant work is bounded by the chosen orientation and the hot loops use minimal index arithmetic.
