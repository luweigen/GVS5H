- **Run reduction:** Compress maximal equal blocks into weighted runs. A deletion can be assumed to delete the complete first run: deleting a strict prefix leaves the same value at the front and is never better than deleting that complete run at once.

- **Run-count accounting:** Every whole-run deletion lowers the run count by one. A swap lowers it by two exactly for `x^p, y, x, y^q`, where the two middle runs both have size one. Swapping those middle elements gives `x^(p+1), y^(q+1)`. If the initial number of runs is `m` and `r` such rewrites are used, there are `m-2r` deletions and total cost is `m-r`.

- **Greedy structural result:** An optimal operation sequence can use only the two-run-decreasing rewrites. Among maximum-cardinality rewrite sequences, there is one whose first rewrite is the leftmost currently applicable rewrite. Exchange arguments for overlapping alternating windows establish this, so repeatedly applying the leftmost available rewrite maximizes `r`.

- **Linked-list representation:** Each original run has an immutable index. `prv` and `nxt` link precisely the current live runs; after a rewrite at `left,b,c,right`, only `b,c` are removed and the edge `left-right` is created. The outer nodes remain alive and receive size increments. For every alive node, following `nxt` visits the next alive node, so `applicable` never reaches a dead node after its initial alive check.

- **Affected candidate starts:** A candidate starting at `p` reads the four live nodes `p,nxt[p],nxt[nxt[p]],nxt[nxt[nxt[p]]]`. A rewrite changes only the sizes of `left` and `right` and the local adjacency replacing `left-b-c-right` by `left-right`. Thus any newly changed candidate must have `left` or `right` in its four-node window. Its start is consequently that node or one of its preceding three live nodes. `add_near(left)` covers all starts involving `left`, including the new `left-right` boundary. `add_near(right)` is redundant because `left` is then its predecessor, but is safe and explicitly covers every window involving `right`.

- **Heap correctness and stale safety:** Original indices preserve left-to-right order even after deletions. Heap minimum therefore selects the leftmost scheduled node. Initially every node is scheduled. A node whose applicability can change is rescheduled by the affected-window rule. Entries can be stale due to deletion or later local rewrites; `applicable` checks liveness, current links, current sizes, and values, so stale entries are harmless. Hence when a valid entry is popped, no smaller current candidate exists unscheduled or pending, and it is the greedy leftmost rewrite.

- **Complexity:** There are at most `floor(m/2)` rewrites. Heap initialization has `m` entries. Each rewrite performs at most eight pushes, so there are `O(m)` total pushes and pops, each `O(log m)`. Applicability tests and list updates are `O(1)`. Total time is `O(m log m)` per case and `O(sum N log N)` overall. Arrays, run storage, and heap use `O(m)` memory; input storage is `O(sum N)`.
