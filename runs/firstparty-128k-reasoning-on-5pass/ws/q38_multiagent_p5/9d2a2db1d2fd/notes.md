- **Core reduction:** For any route, let M be the minimum building height on the route. Walkways are free at a fixed floor, so the optimal stair count for that route is |y-z| if M >= min(y,z), otherwise y+z-2M. This cost only decreases as M increases, so the best route only needs the largest M for which start and end blocks are connected using blocks of height at least M.
- **Bottleneck value:** That largest M is the maximum bottleneck between the two cells. On the grid, put an edge between adjacent cells with weight min(F_u,F_v). For different cells, a path's minimum node height equals its minimum edge weight. Kruskal in descending edge weight therefore connects components exactly as the threshold subgraph of cells with F >= threshold grows; the weight when two query endpoints first meet is the answer's B.
- **Offline resolution:** Each unresolved query id is kept in the pending set of each endpoint's current component. When two components merge at weight w, ids present in both sets are resolved with B=w and removed; ids present in only one set are moved to the merged component. Same-block queries are preanswered with B=F[cell].
- **DSU details:** Union by number of cells keeps find depth small. For pending sets, merge the smaller set into the larger to keep set operations amortized small. The root is chosen by cell size, but the surviving set object may be either component's set; it is assigned to the new root. Empty sets are discarded.
- **Set merge optimization:** For very small sets, a direct Python loop does membership, removal of common ids, and insertion of non-common ids. For larger sets, use C-level set operations: common = small & large, assign w to all common ids (skip assignment if w==1 because bot is initialized to 1), subtract len(common) from remaining, then difference_update and update. This keeps Python loops mostly over resolved ids.
- **Input and packing:** Read all integers with list(map(int, read().split())) for speed, slice F, process queries, then delete the input list. Pack each grid edge as (w << 40) | (u << 20) | v; 20 bits are enough for cell indices up to 250000. Sorting packed integers descending is faster and uses less memory than tuples.
- **Answer formula:** After the sweep, bot[q] holds B (initial 1, so unresolved or bottleneck-1 queries are already correct). If B >= min(y,z), answer abs(y-z); otherwise answer y+z-2B.
- **Complexity:** O(HW log(HW) + Q log Q) in practice for sorting and set moves, memory O(HW + Q + edges). H,W <=500 gives about 250k cells and 500k edges; Q <=200k.
- **Edge cases:** N=1 or all queries same-block skips edge generation. H=1 or W=1 works because missing edge loops are empty. Bottleneck is at least 1 because all F>=1. Early stop when remaining different-block queries reach 0.
