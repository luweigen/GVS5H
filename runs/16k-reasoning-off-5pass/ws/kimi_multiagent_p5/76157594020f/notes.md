
## ideation
- Core difficulty: deciding feasibility for a candidate max run length L, i.e., computing the minimum flips needed so that no run of identical characters exceeds L.
- Key structural fact: flipping a bit inside a run of length m breaks it into pieces; to keep every piece ≤ L, the minimum flips within that run is floor(m / (L+1)) — place flips at positions L+1, 2(L+1), ... within the run. Runs are independent because flips only affect their own run (a flipped bit becomes a singleton of the opposite char, length 1 ≤ L for L ≥ 1... careful: a flipped bit adjacent to a neighboring run of the opposite char could merge — but flipped positions are interior separators; for L ≥ 2, placing flips strictly inside the run with spacing L+1 keeps them isolated from boundaries as long as we don't flip at the run edges adjacent to opposite runs. Actually flipping at position L+1 from the run start: the flipped bit could be adjacent to the previous run's last char (opposite of current run's char = same as flipped bit) only if L+1 = 1, i.e., L = 0, impossible. For L ≥ 1, the first flipped position is at offset L ≥ 1 within the run, so it's not at the boundary... wait, offset L means index L (0-based), and the boundary is index -1 relative, so adjacency to previous run only if flipped index is 0 of the run, which happens only if L = 0. So safe for L ≥ 1. Hmm, but for L = 1, flipped positions are at offsets 1, 3, 5, ... — the flipped bit equals the neighboring runs' char and could merge with adjacent runs across boundaries, creating runs of length up to 3 (e.g., "1|0 1 0|1" flipping middle). That's why L = 1 needs separate handling: the whole string must be alternating, so just count mismatches to the two target alternating patterns.
- Alternative approach: DP over positions with state = current run length and char — O(n^2 * numOps) too slow conceptually but n ≤ 1000 so O(n * L * ops) might pass; however the greedy formula is O(n) per check, total O(n log n), much cleaner.
- Pitfalls:
  - L = 1 special case (merging across run boundaries invalidates the floor(m/(L+1)) formula — actually check: does the formula fail for L=1? Run "000" with L=1: formula gives floor(3/2)=1 flip → "010", runs of 0 have length 1, fine within the run. Merging requires flipped bit adjacent to opposite run: flipped bit at run offset 0 or last. For L=1, offsets are 1,3,5,...; if run length m is even, last flipped offset is m-1 (the last char), which is adjacent to the next run! E.g., s = "0011", L=1: run "00" flip offset 1 → "01", run "11" flip offset 1 → "10", result "0110" — middle "11" run length 2 > 1. Formula gives 1+1=2 flips but answer needs the string alternating: "0101" needs 2 flips too here.   - Binary search bounds: answer is at least 1 and at most n (numOps could be 0 with one long run).
  - Monotonicity: if L is feasible, any L' > L is feasible (fewer constraints), so binary search is valid.
- Complexity: O(n log n) — well within n ≤ 1000.
