
## ideation
The core difficulty is computing the minimum number of moves required to visit each index `i` at least `k_i` times, starting from index -1. The path is a walk on a line graph. To visit all nodes up to `n-1`, we must at least reach `n-1`. The minimum moves to simply reach the end is `n`. Any extra moves must be used to satisfy the visit counts `k_i`. An optimal strategy would involve moving back and forth. For example, to add visits to a set of nodes, it's most efficient to find the rightmost node that still needs visits, say `j`, and perform an excursion from `j-1` to `j` and back, which costs 2 moves and adds one visit to `j`. This suggests a greedy approach: iterate from right to left, and for each position `i`, calculate the number of additional visits needed. These additional visits can be "simulated" by moving back and forth between `i` and `i-1`. The total moves would be `n` (to reach the end) plus the sum of these extra moves. A key insight is that an extra visit to `i` can be combined with an extra visit to `i+1` in a single "back-and-forth" maneuver from `i` to `i+1` and back to `i`. This costs 2 moves and adds one visit to both `i` and `i+1`. This leads to a greedy calculation where we process from right to left, carrying over the "extra visits" from the right.

A potential pitfall is correctly handling the "at most m moves" constraint. If the minimum required moves is `min_moves`, and `min_moves <= m`, the target is achievable. The parity of `m - min_moves` might matter if we must use exactly `m` moves, but since it's "at most", we can always waste moves by going back and forth, so any `m >= min_moves` works.

- Re-derived the greedy `check`:
  - To give every index `i` a score ≥ target, index `i` must be visited `k_i = ceil(target / points[i])` times.
  - Walking from -1 to `n-1` costs `n` moves and gives each index its first visit.
  - Processing right to left, let `carry` be the extra visits position `i` receives from excursions across edge `(i, i+1)` (each such excursion ends back at `i`, giving it one extra visit). Position `i` still needs `need = k_i - 1 - carry` more visits. Each missing visit is supplied by an excursion across edge `(i-1, i)` costing 2 moves and simultaneously giving `i-1` one extra visit, so `carry = need` for the next (leftward) iteration. If `need <= 0`, no excursions are needed here and `carry = 0` (surplus visits from the right cannot be transferred further left, since excursions ending at `i` from the right don't cross edge `(i-1, i)`).
  - Total moves = `n + 2 * sum(need)`. Target is feasible iff this is ≤ `m` (extra moves can always be wasted by going back and forth, so "at most m" is fine).
