
## ideation
Core difficulty: choosing a minimum set of paid operations (each costs 1) and their types so every position gets set to 1 at least once. Since setting 1s is monotone (never resets), only coverage matters, and order is irrelevant.

Key structural insight:
- 0 paid ops never works (N ≥ 1).
- 1 paid op works iff some operation has [L,R] = [1,N] using op1 (op2 with [1,N] covers nothing).
- 2 paid ops suffice whenever any solution exists. Case analysis for a pair (i, k):
  - op1+op1: intervals must union to [1,N]: need L_i=1, R_k=N (or vice versa) with R_i ≥ L_k − 1.
  - op2+op2: complements union to [1,N] iff intervals are disjoint: R_i < L_k or R_k < L_i.
  - op1(i)+op2(k): uncovered region is [L_k,R_k] \ [L_i,R_i]; full coverage iff L_i ≤ L_k and R_i ≥ R_k (interval i contains interval k).
- Claim: if any finite set of paid ops covers [1,N], then some pair (or single op) does. Intuition: consider the leftmost-covering and rightmost-covering choices; e.g., with only op1s, the op with L=1 and the op with R=N must have overlapping intervals; mixing op2s reduces to the containment/disjointness conditions above. So checking 1 and 2 suffices; otherwise answer is -1.

Pitfalls:
- N up to 1e6, M up to 2e5 → need O(M log M) or O(M + N) checks; O(M²) pair enumeration too slow.
- For op1+op2 containment: need to know if there exist i,k with L_i ≤ L_k and R_i ≥ R_k (i ≠ k; careful when same operation could serve both roles — if [L_i,R_i]=[L_k,R_k] with i=k, op1+op2 on the SAME operation is not allowed since each operation picks exactly one type; but i=k with containment means equal intervals, which would require using the same operation twice — not allowed. However if L_i=L_k and R_i=R_k with i≠k it's fine).
- For op1+op1: need min L among ops with... actually need an op starting at 1 and an op ending at N with overlap; they could be the same op ([1,N]) but that's the 1-op case anyway.
- For op2+op2: need two disjoint intervals; track min R and max L.

Efficient checks:
- op2+op2: exists pair with R_i < L_k ⟺ min R < max L (and the argmin/argmax indices differ automatically since R < L strict).
- op1+op1: exists i with L_i=1, k with R_k=N, R_i ≥ L_k − 1. Track max R among L=1 ops, min L among R=N ops.
- op1+op2: need i≠k, L_i ≤ L_k, R_i ≥ R_k. Sweep: sort by L; for each k, query if any i with L_i ≤ L_k has R_i ≥ R_k, excluding i=k. Handle ties carefully: process groups of equal L, query structure built from previous... actually containment allows equal L only if R differs or different index. Simplest: sort ops by L ascending; maintain max R seen so far with its index; for each k, if max R ≥ R_k and (index ≠ k or second-best works). Edge: when L_i = L_k and R_i = R_k and same index — need a different i. Keep top-two (R, idx) per prefix to handle exclusion.
