
## ideation
The core difficulty is that smoke accumulates over time: new smoke spawns at the origin whenever the origin is empty after the wind move, and we must answer N queries about a fixed cell (R,C) at half-integer times. N up to 2e5 rules out simulating a set of positions directly if it could grow large — but actually the set of smoke positions grows by at most one per step (one new birth per time step), so the total number of distinct particles is at most N+1. The key insight is to work in a "wind-relative" frame: after t steps, every particle has been shifted by the same cumulative displacement D_t. A particle born at time k (born at origin right after the k-th wind move, or the initial particle at k=0) is located at D_t - D_k at time t+0.5. So the state is fully captured by the set B of birth-time displacement vectors D_k. Then:

- Smoke at (R,C) at time t+0.5 iff (R,C) = D_t - D_k for some k in B, i.e., D_t - (R,C) ∈ B.
- Origin is empty after wind move at time t iff no particle sits at origin, i.e., 0 = D_t - D_k, i.e., D_t ∈ B. If D_t ∉ B, a new particle is born: add D_t to B.

Both checks are O(1) with a hash set of (x,y) tuples. Pitfalls: (1) the initial smoke at t=0 corresponds to D_0 = (0,0) being in B from the start; (2) the birth happens after the wind move at the same time t, so the check for origin emptiness and the query at t+0.5 must both use D_t, and the newly born particle (added at time t) is at origin at time t+0.5 — since (R,C) ≠ (0,0), adding D_t to B before or after answering the query at time t doesn't affect the answer for (R,C) at time t, but order matters for correctness of subsequent steps; safest order per step: update D_t, check query using B (before insertion — but since (R,C)≠(0,0), D_t - (R,C) ≠ D_t, insertion wouldn't change the query result anyway), then check origin emptiness and insert D_t if empty. Actually cleanest: update D_t; if D_t ∉ B, add D_t to B (birth); then answer query by checking D_t - (R,C) ∈ B. Both orders give identical results for the query because the newly added element D_t can only match the query if (R,C)=(0,0), which is excluded. (3) Coordinate convention: define displacement vectors matching the movement directions (N: (-1,0), S: (+1,0), W: (0,-1), E: (0,+1)) and accumulate. (4) Use tuples or encoded integers (e.g., x * 400001 + y offset) for hashing speed; tuples are fine in Python for 2e5.

Worked in the wind-relative frame: after t wind steps with cumulative displacement D_t, a particle born at time k (at the origin) sits at D_t − D_k. The set B holds the birth displacements D_k (starting with D_0 = (0,0) for the initial smoke). At each step: update D_t from S[t]; if D_t ∉ B then the origin was empty after the wind move, so a new particle is born — insert D_t into B. Smoke exists at (R,C) at time t+0.5 iff D_t − (R,C) ∈ B. Since (R,C) ≠ (0,0), inserting D_t before the query cannot change the query result. Each step is O(1) hash-set work, O(N) total, O(N) memory.
