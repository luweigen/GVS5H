The constraints $r < 10^9$ mean we cannot iterate through all numbers. We need a digit DP approach. The key observation is that the sum of digits $S$ for a number up to $10^9$ is at most $9 \times 9 = 81$ (for 999,999,999). The product of digits $P$ must be divisible by $S$. We can define a DP state as `(position, current_sum, current_product_gcd_state, is_less, is_started)`. However, tracking the full product is too large. Instead, we can track the product modulo some values or use the fact that we only care if $P \% S == 0$. A better approach: since $S$ is small, we can iterate over all possible sums $S$ from 1 to 81. For each fixed sum $S$, we count numbers where the digit sum is $S$ and the digit product is divisible by $S$. We can use digit DP to count numbers with digit sum $S$ and check the product condition. But checking product divisibility for each number is hard in DP. Alternative: Use digit DP with state `(pos, current_sum, current_product_factors)`. Since $S \le 81$, the product must be divisible by $S$. We can track the product's prime factorization or simply track the product modulo $LCM(1..81)$ which is too big. Better: Track the product as a value, but prune states where product becomes too large? No. Insight: For a fixed sum $S$, we need $P \equiv 0 \pmod S$. We can do digit DP that tracks `(pos, current_sum, current_product_mod_LCM)` but LCM(1..81) is huge. Instead, note that we only need $P \% S == 0$. We can iterate $S$ from 1 to 81, and for each $S$, run a digit DP that counts numbers with digit sum exactly $S$ and digit product divisible by $S$. The DP state: `(pos, current_sum, current_product_mod_S, tight, started)`. Since $S \le 81$, `current_product_mod_S` has at most 81 states. Total complexity: $81 \times 10 \times 81 \times 2 \times 2 \approx 500,000$ per query for $S$, and 81 values of $S$, so $\approx 40M$ which might be tight but acceptable in Python with optimization. Actually, we can combine all $S$ into one DP? No, because the modulus changes.
