- Key fact: for a fixed subarray, the optimal strategy is greedy left-to-right: maintain running max `mx`; each element must be raised to at least `mx`, so cost = Σ (mx_i − a_i) where mx_i is the prefix max. Raising anything more never helps.
- Monotonicity: extending a subarray to the right never decreases its cost (new element either adds 0 if ≥ current max, or adds (max − a)). So for each left endpoint `l`, valid right endpoints form a contiguous prefix → two pointers / sliding window works: for each `l`, find max `r` with cost(l..r) ≤ k, add (r − l + 1).

## worker: Implement the full solution: two pointers iteratin
- **Cost of a subarray**: the minimum number of +1 operations to make `nums[l..r]` non-decreasing is `Σ (M_i − nums[i])` where `M_i = max(nums[l..i])` (greedy left-to-right raising to the running max is optimal; raising more never helps).
- **Monotonicity**: `cost(l..r)` is non-decreasing when the window grows in *either* direction. Hence, iterating `l` from `n−1` down to `0`, the maximal valid right endpoint `r_l` satisfies `r_l ≤ r_{l+1}`, so `r` only moves left — total pointer movement is O(n).
- **Data structure**: a deque of `[value, count]` blocks representing the running-max step function of the current window (positions partitioned into contiguous blocks of equal `M_i`; block values strictly increase front→back; the back block's value is the window maximum).
  - **Prepend `x = nums[l]`** (front): old positions with `M_i < x` get raised to `x`. These are exactly the front blocks with `value ≤ x`; pop them, add `(x − v)·c` to cost, and merge them plus the new element into one front block `[x, 1 + Σc]`. Each block is pushed once and popped once → amortized O(1).
  - **Remove from right** (`r -= 1`): position `r` always lies in the back block (its `M_r` is the window max), and removing it cannot change any other position's running max (those depend only on elements to their left). So `cost -= back_value − nums[r]`, decrement the back block's count, pop if empty. This is exactly correct — unlike left-removal, which would require recomputing running maxima (the reason for iterating `l` downward and shrinking `r` from the right instead of the usual left-shrink sliding window).
- **Verification**:
  - Example 1 (`nums=[6,3,1,2,4,4], k=7`): per-`l` valid counts are 2,5,4,3,2,1 → total 17. ✓ (Traced: at `l=0`, prepending 6 raises cost to 16; right-removals give costs 14, 12, 8, 3, stopping at `r=1` since `cost([6,3,1])=8>7` but `cost([6,3])=3≤7`.)
  - Example 2 (`nums=[6,3,1,3,6], k=4`): counts per `l`: `l=4`:1, `l=3`:2, `l=2`:3 (`[1,3,6]` cost 2), `l=1`:3 (`[3,1,3,6]` cost 1, length-4 window valid), `l=0`:3 (`[6,3,1]` cost 8>4, `[6,3]` cost 3 ok) → 1+2+3+3+3 = 12. ✓
- **Edge cases**: `n=1` → returns 1 (single element always valid, cost 0). `k` up to 1e9 and values up to 1e9: costs can reach ~1e14 and the answer ~5·10⁹; Python ints handle this. The `while cost > k and r >= l` guard keeps the window non-empty; since a single element always has cost 0 ≤ k, the loop always terminates with `r ≥ l`.
- **Complexity**: O(n) time (each index prepended once, each block popped at most once, `r` moves left at most n times), O(n) space for the deque.
