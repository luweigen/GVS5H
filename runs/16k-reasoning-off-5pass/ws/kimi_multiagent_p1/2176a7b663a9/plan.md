Intervals connect when disjoint, i.e., when one ends before the other starts (R_i < L_j or R_j < L_i). Sort intervals by R; then edges only exist between an interval and intervals entirely to its left or right. Key structural fact: within the "overlap" order, the graph is a comparability-like graph where we can build a sparse auxiliary graph preserving connectivity and distances. A standard trick: sort by R, and connect each interval to the interval with maximum R among those ending before L_i (and symmetric), forming a small graph (O(N) edges) that preserves connected components; then run Dijkstra from each query source — but Q is large, so instead note vertex-weighted shortest paths can be answered via multi-source structure only if queries are offline with few sources — they're not. Better: the component structure is an interval overlap complement; shortest path weights can be computed with 0-1 style reduction: transform vertex weights to edge weights (cost of entering a vertex), build sparse graph with O(N) edges using segment-tree/bidirectional "nearest non-overlapping" links, then answer each query with Dijkstra per query — too slow. Instead, observe queries need min-weight path in a graph where a BFS-like "Dijkstra from s" over the sparse graph is O(N log N); with Q up to 2e5 we need faster: precompute nothing global since weights are vertex-based and pairs arbitrary. Realistically intended solution: build O(N)-edge graph preserving pairwise shortest path distances exactly (via connecting each interval to best neighbors in sorted order), then run Dijkstra once per query is still too slow — so the intended approach is likely that the sparse graph has special structure (a path/caterpillar) allowing O(1) or O(log N) queries via prefix minima. Workers should verify structure and design accordingly.
