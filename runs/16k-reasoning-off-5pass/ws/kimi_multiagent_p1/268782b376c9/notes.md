The problem asks to maximize the minimum gameScore after at most m moves on a line, starting at index -1, forced first move right, and each move lands on an index and adds points[i].

Core difficulty: translating a target minimum score X into the minimum number of moves needed to achieve it. Since each visit to index i adds points[i], achieving gameScore[i] >= X requires at least v[i] = ceil(X / points[i]) visits to index i. The path constraint (start at -1, move by ±1, stay within [0, n-1] after first move) means visits to deeper indices are "expensive" and revisiting requires backtracking.

Candidate feasibility formula: to give index i at least v[i] visits, we need at least i + 1 moves to reach it the first time, and each subsequent visit requires at least 2 extra moves (leave and return). So a lower bound is max over i of (i + 2*v[i] - 1). This is also achievable: go all the way to the rightmost needed index, then bounce appropriately; the binding constraint is the index maximizing i + 2*v[i] - 1. ## worker: finalize
- **Model.** For a target minimum score `X`, index `i` needs `v[i] = ceil(X / points[i])` visits. Let `x_i` be the number of crossings of edge `(i-1, i)` (edge 0 = entry from -1 into 0). Total moves = `sum x_i`. With end position `e`: `x_i >= 1`, `x_i` odd iff `e >= i`, and `x_i + x_{i+1} >= 2*v[i] - [e == i]` (with `x_n = 0`). These conditions are necessary (each visit to `i` is entered/exited through its two incident edges) and sufficient (on a line, any crossing counts with correct parities are realizable by a walk).
- **Greedy per end.** For fixed `e`, processing right to left taking the smallest feasible `x_i` is optimal: increasing `x_{i+1}` by 2 (parity-preserving) lets `x_i` drop by at most 2, a net-zero trade, so the minimal sum is achieved by the greedy.
- **Parity simplification.** Right of `e` all parities are even → one suffix precompute (`sx`, `ssum`). Left of `e`, inputs are always odd; for odd `t`, `2*v[i] - t` is already odd, so the odd-parity rounding disappears and `x_i(t) = max(1, D_i - t)` exactly. Hence each prefix function is a composition of clamp functions, piecewise linear with slopes in `{−1, 0}` for `x` and integer slopes for the cumulative sum — representable as a compact breakpoint list.
- **Segment tree of composed functions.** `compose(A, B)` merges two breakpoint lists by a two-pointer sweep (B applied first, threading its output range through A's breakpoints right-to-left), merging adjacent collinear segments. Querying a prefix `[0, e-1]` decomposes into O(log n) canonical nodes threaded right-to-left.
- **Binary search.** Feasibility `min_moves(X) <= m` is monotone; "at most m moves" is fine because leftover moves can always be burned bouncing (only adds score). Upper bound `max(points) * (m + 1)` is safe (visiting only index 0 every move gives `points[0] * m`, and the bound covers all cases).
- **Validation performed during development.** Hand-checked against both examples (`[2,4], m=3 → 4`; `[1,2,3], m=5 → 2`) and against the edge-crossing LP on `v=[3,2,1] → 7`, `v=[2,1,1] → 5`, `v=[1,5,1] → 10` (middle end strictly optimal — confirming all end positions must be considered), `v=[5,1,1] → 11`, `v=[1,1,5] → 11`. A brute-force DFS cross-check harness (memoized over `(pos, capped visit counts, moves_left)`) was built and used to validate the fast path on all small inputs (`n ≤ 4`, `m ≤ 12`); it caught and helped fix two real bugs (an unrepresentable "identity" padding node in an iterative tree — replaced with a recursive build over exactly `[0, n-1]` — and a faulty node-collection guard in `query_prefix`). The final submission keeps only the fast path for cleanliness and speed.
- **Complexity.** Feasibility check: build O(n) node compositions; each compose output size is O(size A + size B) with collinear merging, giving O(n log n) total build work in the worst case and O(log² n)-ish per prefix query; overall check ≈ O(n log n), times ~31 binary-search iterations — comfortable for `n = 5·10⁴` in Python given the small constants (lists of tuples, iterative loops).
