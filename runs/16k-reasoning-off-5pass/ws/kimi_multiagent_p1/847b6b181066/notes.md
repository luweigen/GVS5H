
## ideation
Core difficulty: N up to 200k, so we need O(N) or O(N log N); we cannot simulate a set of smoke cells explicitly (it can grow to size N). The key insight is that wind translates ALL smoke uniformly, so smoke positions are determined by birth times. Let P_i = cumulative displacement after i wind steps (P_0 = (0,0)). Smoke born at time k (k=0 initial, or generated after step k) sits at position P_t - P_k at time t. So (R,C) is occupied at time t iff there exists a valid birth time k with P_k = P_t - (R,C). Similarly (0,0) is occupied at time t iff some valid birth k has P_k = P_t. So maintain a hash set of P_k values for all actual birth times k (0 ≤ k ≤ current t). At each step t: update P_t from S[t-1]; answer bit = 1 if (P_t - (R,C)) ∈ set; then generation: if P_t ∉ set (campfire empty), add P_t as a new birth point. Initialize set with P_0 = (0,0). This is O(N) with a Python set of integer-encoded coordinate pairs.

Pitfalls:
- Order of operations per step: wind first (check occupancy at t+0.5 after wind), then generation at (0,0) — generation at time t affects time t+0.5? Generation happens at time t (after wind), and we query at t+0.5, which is after generation. So the newly generated smoke at (0,0) at time t IS present at t+0.5. So the check for (R,C) at t+0.5 must include births at time t. Since (R,C) ≠ (0,0), the birth at t is at (0,0) ≠ (R,C), so it doesn't affect the answer bit anyway — but to be safe, add P_t to the set BEFORE checking membership for the answer? No: smoke born at time t is at position P_t - P_t = (0,0) at time t+0.5, so it only matters if (R,C)=(0,0), which is excluded. Either order works for the answer, but the generation condition "(0,0) empty at time t" must be evaluated using births k < t... actually births at time t happen only if empty, so checking P_t against the set of births k ≤ t-1 (plus initial) is correct. Cleanest: compute answer bit using set (births ≤ t-1 don't include t, but birth at t is at (0,0) ≠ (R,C) so irrelevant), then check P_t ∉ set → add. Both orders give identical results given the constraint (R,C)≠(0,0).
- Encode coordinates as a single integer (e.g., r * (2N+5) + c offset, or use tuples — tuples are fine speed-wise for 200k, but int encoding is faster; use (r << 32) ^ c style or r * 400005 + c + offset to avoid hash collisions issues — Python tuples hash fine, but int is cheaper).
- Displacement directions: N → r decreases by 1; S → r+1; W → c-1; E → c+1.
- P_t - (R,C): target birth coordinate = (pt_r - R, pt_c - C).
- Range of coordinates: within [-N, N], so encoding with base (2N+1) works.
