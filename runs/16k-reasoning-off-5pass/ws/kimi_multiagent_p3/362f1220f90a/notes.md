
## ideation
The core difficulty is handling overlapping constraints: 'T' positions force exact substrings equal to str2, which can conflict with each other (requiring consistency checks via str2's self-overlap/border structure), while 'F' positions forbid exact matches, requiring us to "break" any accidental match minimally. Lexicographic minimality pushes us to default to 'a' everywhere and, when breaking an F-match, modify the rightmost free position in the window with the smallest possible change. A subtlety: changing a character to break one F-window could create a new match in an overlapping F-window, so re-checking is needed. Also, an F-window fully covered by T-forced characters that equals str2 means infeasibility. Efficient tracking of forced vs. free positions (e.g., difference array for coverage counts) matters since n ≤ 10^4 and m ≤ 500 (O(n·m) is borderline acceptable at 5·10^6, but smarter is safer).

**Complexity analysis of the previous full-rescan version:**
- Each `while changed` pass costs O(n·m) (scan all n starts, each `matches` up to O(m)).
- Each fix strictly increases one position's character by 1; characters never decrease, so total fixes ≤ 25·L ≈ 25·10⁴ = 2.5·10⁵.
- Worst case: one fix per pass → up to 2.5·10⁵ passes × 5·10⁶ ops/pass ≈ **1.25·10¹² operations** — far too slow. Even in moderate cases (many fixes per pass), adversarial inputs (e.g., str1 = "FF...F", str2 = "aaa...a") force one fix per pass in the worst interleavings, so the full-rescan approach is not safely within limits.

**Fix applied (as tasked): queue of affected F-windows.**
- Initialize the queue with all F start indices.
- On editing position `pos`, only windows containing `pos` can change match status; those have start indices in `[pos - m + 1, pos] ∩ [0, n-1]`. Re-enqueue exactly those F-starts (with an `in_queue` dedup flag).
- Each queue pop costs O(m) for the `matches` check (plus O(m) for the fix scan when it matches).
- Number of enqueues: initial n, plus ≤ m per fix; fixes ≤ 25·L.
